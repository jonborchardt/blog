## TL;DR

Agentic coding isn't "write a giant prompt and hope." It's an engineering process for moving ambiguity out of my head and into plans, code, validation, and repository rules. This process helps me start a project in good state.



The main shift isn't that Claude writes more code. It's that I'm designing a system in which future agent sessions are less likely to do the wrong thing, because the repo itself pushes back.

The rest of this post walks that process end to end on one real case study: this blog, the site you are reading. The process has three beats: decide before you prompt, let the repository replace the prompt, and treat validation as the real output. The result is a static site where, on every push, CI proves that:

- **Lighthouse scores 100/100/100/100** on representative pages
- **every page passes an axe WCAG 2.2 AA audit** and the W3C Nu markup validator
- **prose pages ship zero JavaScript**
- **the build fails** on a broken link, a missing alt, an unknown tag, or any admin output in `dist/`

Those are not goals. They are a floor the repo enforces, and a red check blocks the deploy.

Each section opens with this rail of the process: the three beats, the eleven stages inside them, and the bold stage is the one we're in.

## The idea for the case study

The concrete example is a new static technical blog. The app is intentionally modest; the workflow is the interesting part. The core constraints were a GitHub Pages project site served under `/blog/`, static pages, MDX posts, React only for interactive islands, search with no external service, a local-only admin, and no analytics, comments, CMS, or backend, all while meeting accessibility, SEO, performance, and responsive-behavior targets. That is not a huge application, but routing, static generation, MDX, React islands, client-side search, SEO, accessibility, dev-only admin tooling, and GitHub Pages deployment constraints are enough moving parts to exercise the process.

The blog was just a convenient product. The real object being built was an agent-maintainable codebase, and agentic coding raises the value of executable constraints. "Agent-maintainable" meant explicit contracts, typed schemas, deterministic file organization, validation, reusable primitives, build-time failures for invalid states, straightforward conventions, low ambiguity, and clear instructions for future agents. Instead of relying on future agents to remember instructions, I want the repo itself to reject bad states. Each human convention should become a repository contract, and each contract should become a machine-checkable invariant. In practice that means an unknown tag, a broken internal link, and admin content in `dist/` are all build failures.

Before asking Claude to code, I used ChatGPT to interrogate the idea and expose hidden architectural decisions. The reusable pattern is simple: do not ask for the implementation prompt until the model has asked you what decisions are missing. ## The first model exposed the real forks

ChatGPT turned the bag of requirements into specific architectural choices. These were the forks that mattered:

<ListGrid>

- Markdown vs MDX
- SPA routing vs emitted static HTML
- pure React/Vite vs Astro + React
- MUI vs publication-oriented design primitives
- centralized metadata vs free-form frontmatter
- global components vs post-local components
- client-side search vs hosted search
- local-only drafts vs draft visibility in production
- config-driven featured content vs post metadata
- static site vs runtime backend
- how much validation belongs at build time

</ListGrid>

If I had skipped this step, Claude would have silently made those choices, some fine, some wrong. The problem is not just wrong decisions; it is invisible ones. An invisible architecture decision becomes expensive to reverse because it gets baked into the first code generation pass, and by the time you notice it, half the codebase assumes it.

## I answered decisions, not trivia

I made product and architecture calls but avoided over-prescribing implementation details. The division of labor is that the human decides invariants and the agent decides implementation mechanics while executing. The decisions I locked looked like this:

```text

Static HTML: yes
React islands inside MDX: yes
Astro: yes
```

I did not need to dictate the exact Node version, the Astro APIs, the component implementation, the shape of test files, etc. The invariant mattered more than the implementation. "`/admin/` must not exist in production output" is an invariant; the precise Astro/Vite mechanism that guarantees it is an implementation detail, and the agent is better placed than I am to pick it once it can see the real toolchain.

## We locked the URL model

The `/blog/` deployment path was a major constraint. We handled it as a deployment base rather than a source-folder structure, and it later became a validation target. The final public routes were:

```text
https://jonborchardt.github.io/blog/
https://jonborchardt.github.io/blog/all-posts/
https://jonborchardt.github.io/blog/<post-slug>/
https://jonborchardt.github.io/blog/series/
https://jonborchardt.github.io/blog/series/<series-slug>/
https://jonborchardt.github.io/blog/about/
```

The rule that came out of this was that Astro gets `base: "/blog"`, but nobody hardcodes `/blog/` into application routes, nobody creates `src/pages/blog`, and every link goes through Astro's base/site URL utilities. Base-path handling is exactly the kind of thing agents get wrong, because the site works locally and breaks in production. So I wanted it to be a first-class invariant from the start, not a late deployment fix.

## We decided how posts live in the repo

Posts are self-contained MDX directories with colocated assets and optional post-specific components. The principle is to allow local weirdness and keep shared abstractions clean. A post looks like this on disk:

```text
src/content/posts/
  some-post/
    index.mdx
    hero.webp
    architecture.svg
    demo-data.json
    components/
      SomeVisualization.tsx
```

The important component rule is not to force bespoke MDX React components into the global reusable library. Reusable article primitives live in `src/components/blog/`, but a weird visualization that belongs to one article stays with that article, and if it later proves generally useful it gets promoted. This matters for agent-authored content specifically. Agents are likely to create unusual diagrams, visualizations, and demos for specific posts, and if every one-off artifact lands in the shared component library, the design system becomes a junk drawer. Post-local components let agents be creative without degrading the global architecture.

## Prompt 1: build the skeleton, not the product

Now that we had some idea of the architecture, it was time to start building, but not the features. For projects like this, I split project setup from implementation. The first prompt on any project is about the skeleton only: architecture, dependencies, file structure, contracts, tooling, and validation, with no features. Features come later, in separate prompts, once the foundation is in place and the agent has something solid to build on. So the first Claude prompt explicitly said the goal was **not** to build the finished blog. The opening constraint read:

> The goal of this task is not to build the finished blog.
>
> The goal is to establish the correct architecture, dependencies, file structure, content contracts, routing model, development environment, validation foundation, and deployment setup so that subsequent work can be done cleanly and incrementally.

The kinds of things that had to be true at the end:

- the project installs, runs locally, and builds
- GitHub Pages deployment is configured
- the major routes exist, with placeholder UI proving the architecture
- MDX posts statically render
- React islands inside MDX work
- the repo structure is ready for future Claude skills and agent-authored posts, etc.

Explicitly out of scope were polished visual design, sophisticated search, the full admin UI, rich blog components, generated social images, and finished product behavior in general. Written non-goals matter because agents drift toward completing things that look incomplete.

# Architectural principle

This is primarily a **statically generated publishing system**.

Astro owns:

- pages
- routing
- layouts
- content loading
- static rendering
- metadata
- build-time behavior

React is for:

- genuinely interactive islands
- interactive visualizations
- interactive demos
- selected client-side tools such as archive search/filtering
- bespoke interactive components embedded in MDX

Do **not** turn the site into a React SPA.

Do not introduce React Router.

Do not hydrate the entire page tree.

Static content should remain static HTML wherever possible.

A normal article containing prose, images, code, and SVG should require little or no client JavaScript.

An MDX article must nevertheless be able to embed a React component and selectively hydrate it when necessary.

## Why "must be true" beats "build something great"

Checkable acceptance criteria cause the agent to verify; vague quality goals cause it to guess. This applies to any prompt that hands work to an agent. From the agent's side, "build me a great blog" forces it to silently make dozens of decisions and hope, whereas "MDX must statically render, a React island must hydrate, URLs must work under `/blog/`, the build must pass" gives it checkable truths. It can run commands and know whether it is done.

It is the same philosophy at two levels: repo contracts help agents maintain code, and plan contracts help agents execute work.

Anything future agents need has to move out of ephemeral chat context and into durable repository or memory artifacts. So before closing the planning session, I asked it directly: do the plans you generated contain everything they need from this conversation, so that I can run each one in a brand new context? That question is a standard step for me at the end of any planning session, because the plans will be executed by sessions that never saw the chat that produced them. 

Claude found a gap: the plan referenced the planning prompt itself, which was unsafe because a future session might receive only "Implement Plan 4" and never see the original product prompt. 

The fix was to add a condensed product spec into the plan document itself, plus a subagent briefing rule that subagent prompts must quote, not summarize, the global constraints, execution notes, product spec, and full plan text. Quote, not summarize. Summarization is where invariants are quietly lost.

Before running the plans, I brought them back to ChatGPT for an independent review, as a reviewer and not as an infinite redesign loop. The review kept the plan intact and added execution guardrails: no opportunistic refactors, validation against a known production preview, one commit per plan. A second model is useful for catching overengineering, detecting architecture drift, challenging speculative fallbacks, strengthening task boundaries, and checking sequencing. But once the repository-aware plan is coherent, wholesale replanning is usually counterproductive.

## Validation became the highest-leverage output

Validation turns architectural and content rules into build failures future agents cannot ignore. Of everything here, this is probably the most reusable lesson for a team. Each gate sits at a different stage and fails on a different class of mistake:

  name="Six validation gates between authoring and deploy"
  summary="A post flows through scaffold checks, the type system, the content-load schema, cross-post validation, built-HTML checks, and end-to-end tests before deploy; each gate fails the process on a different class of mistake."
>

Build failures now catch:

<ListGrid>

- invalid frontmatter
- duplicate slugs
- reserved slugs
- unknown series
- duplicate series order
- unknown tags
- broken internal links
- broken fragments
- missing required alt text
- missing image dimensions
- required SEO metadata problems
- incorrect base paths
- accidental admin output in `dist/`
- TypeScript errors

</ListGrid>

The tag registry is the clearest example of why. Tags and series compile to literal TypeScript unions, so an unknown tag isn't a typo that ages into data drift; it's a type error. That is what kills the entropy many-session authorship otherwise guarantees: the drift toward `ai`, `AI`, and `artificial-intelligence` as three different tags.

A validation error should be an instruction, not just a complaint: it should tell the next agent exactly how to fix the problem. As agent autonomy increases, executable constraints become more valuable than review comments, because review catches bad states after they exist and validation prevents them from shipping.

## The repo ended with its own skills

The process skills used to build the repo were transformed into repo-specific content skills, so the repo now has operating procedures, not just code:

| Skill | Does |
|---|---|
| `write-post` | Draft a complete post: prose, diagrams, hero, validated build |
| `create-hero` | 1500×600 hero contract, SVG-first, rendered via script |
| `create-visual` | Diagram design language + accessibility verification |
| `create-series` | Registry-first series creation |
| `review-post` | Contracts, accessibility, links, SEO, both themes, three widths |

| `wrapup` | Whole-site audit before shipping a batch |

The layered model is that `CLAUDE.md` invariants say what must stay true, skills say how recurring work is done, and validation says what cannot be wrong. This is the end state I want in agent-maintained repos.

## Quality became a floor, not a target

A green build now implies that accessibility, SEO, links, metadata, base paths, and production-safety checks all passed. Early on, quality depended on the model reading a prompt, remembering it, caring about it, and a human noticing if it forgot. By the end, quality depended on the schema rejecting invalid content, validation rejecting broken output, e2e checking rendered behavior, and skills routing work through the right sequence. Claude's own framing of it was:

> Every session I worked on this repo made the next session's mistakes harder to commit.

That is the target property. Concretely, here is what the site passes on every push, and the numbers as they stood at launch:

- **Lighthouse 100/100/100/100** (Performance, Accessibility, Best Practices, SEO) on the home page, a prose post, an interactive post, and the archive, mobile preset, against the production preview.
- **Accessibility:** an axe WCAG 2.2 AA audit of every URL in the sitemap, with zero violations; a keyboard tour (skip link, header, theme toggle, tabs, details, copy button, heading anchors) and a reduced-motion check.
- **Markup:** every built HTML page runs through the W3C Nu validator; markup errors fail the build.
- **JavaScript budget:** prose pages load zero script files; the archive loads only its React island, under 120 KB gzipped; an interactive post loads only the chunks for its own island.
- **Responsive:** no horizontal overflow at 360 px on every sitemap page, including pages with wide tables and code blocks; the archive is usable and axe-clean at 360 px.
- **SEO:** every page has a unique title, a description, a canonical URL that matches its sitemap entry, `og:url`, a reachable 1200×630 `og:image`, a `summary_large_image` Twitter card, and JSON-LD; articles carry `article:*` tags and `BlogPosting` data; RSS, sitemap, and robots.txt all resolve under `/blog/`.
- **Links and assets:** every internal link and `#fragment` resolves; nothing links outside the base path; every image has alt text and dimensions; external links that return 404 or 410 fail the build.
- **Production safety:** `/admin/` returns 404 in the build, asserted twice (dist check and e2e); drafts never appear in pages, listings, RSS, or the sitemap.
- **Theme and dates:** the theme toggle cycles system → light → dark and persists; code blocks switch to the dark Shiki theme; dates render as UTC calendar dates.

None of that is aspirational. Each line is a test or a build check that runs in CI on every push, and a red one blocks the deploy.

## What I actually review after an agent run

My review target moves up from local code style to architecture, scope, validation, and maintainability. The first question is whether the architecture survived: static content stayed static, React remained narrow, the `/blog/` base path stayed correct, no backend crept in, etc. Then, did validation get stronger? If the agent added features but weakened validation, that is a bad trade. Did JavaScript stay justified, with normal articles not turning into interactive applications? Were the deviations reasonable, meaning they preserved invariants while adapting to reality? And did scope stay bounded? Correct code outside the requested boundary is still a process failure.

## Make future mistakes harder to commit

Every agent session should leave behind stronger constraints, not just more code. In this run, the Bash tool mangling `$` and backticks in file writes became a `CLAUDE.md` rule, the port collision became a preview rule, base-path issues became dist checks, tag/series consistency became schema validation, the content workflow became skills, etc.

When an agent discovers a class of mistake, do not just fix the instance. Ask whether it can become a test, a validation rule, a repo instruction, a skill step, or a generator default.

## The initial run was not the end

The plans did not produce a finished site, and I did not expect them to. Over the next several sessions I went back in and added what the program had not covered: a redesigned logo, skill authority and sourcing rules, next-reading suggestions, a table of contents, read time, this post's process rail, an `llms.txt` index, an external link checker, an image lightbox, git-derived last-updated dates, a print stylesheet, a legal page, a WCAG target-size fix for tag pills, abandonment of Mermaid, etc.

These additions were comparatively routine because the repository already encoded most of the constraints they needed to preserve. That is the point. Each feature was a short session against a repository that already knew how to reject a broken state: the schema caught bad frontmatter, the dist checks caught a missing alt or a link outside the base path, the e2e suite caught a layout regression, and the skills routed each change through the same validate-and-build sequence as the original plans. The cost of the validation work in the first session was paid back on every one of these additions, because I could focus my review on the important architectural and behavioral changes, while relying on the validation suite to cover the mechanical invariants it was designed to enforce.

None of them needed a long prompt either. Each was one or two sentences against a repo that already knew its own rules. That is not an argument for a bigger Prompt 1; it is the opposite. Once the constraints live in the repo, when a feature gets asked for stops mattering, because the same schema, checks, and skills police it whether it arrives in the first plan or the fortieth session.

<Details summary="The prompts, one per feature">

**Suggested next reading**

> At the end of every post, show one 'read next' card. The series nav already owns same-series posts, so exclude those and the post itself; pick the post with the most shared tags, tie-break by newest then slug so builds are deterministic, and fall back to the newest eligible post so it is never empty. Put the picker in `src/lib/posts.ts` with a unit test.

**`llms.txt` and raw markdown**

> Serve each post as raw markdown at `/<slug>/index.md` and add `/llms.txt` listing the site name, description, and one line per post linking to its `.md`. Strip MDX imports and components to plain markdown. Both go through `getPosts` so drafts are excluded exactly as in HTML; add `llms.txt` to the reserved slugs. Pure builders in `src/lib/llms.ts` with tests; endpoints under `src/pages/`.

**External link checker**

> After the HTML dist checks, fetch every external link once. Only 404 and 410 fail the build; timeouts, 5xx, 403 bot blocks and 429 are warnings, because those are mostly not our fault. Cache reachable URLs for seven days in `node_modules/.cache`, throttle requests, use `AbortSignal.timeout`, and honour `SKIP_EXTERNAL_LINKS=1` for offline builds. Inject `fetch` so it is unit-testable.

**Lightbox**

> Give `Figure` a `zoom` prop that wraps the image in a button (`aria-haspopup=dialog`) and opens a native `<dialog>` with a close button and the caption as its label. One small inline script in the post layout, delegated by class, so pages without zoomable figures ship no extra JavaScript. Hide the dialog in print and make sure it passes axe.

**Git last-updated**

> Show an 'Updated' date on posts from `git log -1` of the post file, build-time only, memoised per file. Render it only when it is at least seven days after the publish date so launch-week fixes stay quiet. Return nothing outside a checkout or for uncommitted files, and set `fetch-depth: 0` in CI or every file reports the same shallow date.

**Print styles**

> Add print rules in `global.css`: hide chrome per element with `print:hidden`, force the light theme, append external link URLs after the link text, avoid page breaks inside code, figures, tables and blockquotes, wrap long code lines, and hide the lightbox and heading anchors.

**Table of contents**

> Add a left-rail table of contents on posts at desktop widths. Collapsed, it is one bar per heading, bar width proportional to the title, with the current section marked by a scroll listener; on hover or keyboard focus it expands into the clickable 'On this page' list. Hidden in print. No framework, a few lines of inline script, and the anchors must resolve in the dist checks.

**Tag pills**

> Tag pills and nav links must meet the WCAG 2.2 24 px target size.

**Legal page**

> Add a `/legal/` page (privacy, disclaimer, terms) as static MDX under `src/pages/` using the page layout, pulling name and site details from the author and site configs. Link it from the footer as 'Legal & Privacy' and add `legal` to the reserved slugs.

**Read time**

> Show reading time in post metadata: whole minutes at about 230 words per minute, minimum one, counted from the post body with collapsed `<Details>` blocks removed since readers skip those. Pure function with a unit test.

**Navigation cues**

> This post walks a nine-stage process. Add a small 'you are here' rail above each stage's section, listing every stage with the current one filled in, so a reader who scrolls in from the middle knows where they are. Post-local component, static, no script. Also make the table of contents keep the current link scrolled into view when the panel is long.


Every one of those ran through the same skill, the same validation, and the same build, and every one landed green.

## Final takeaway

Use conversation to reduce ambiguity, use a scaffold to discover reality, then plan from the repository instead of the original idea. The useful pattern is not a better giant prompt. The first prompt establishes architecture; the repository then replaces that prompt as the source of truth; the second planning pass turns the real repository into bounded, independently shippable changes. Over time, the important knowledge should leave chat and become code, schemas, tests, validation, repository instructions, and skills. That is what makes this feel less like prompting and more like software engineering.
